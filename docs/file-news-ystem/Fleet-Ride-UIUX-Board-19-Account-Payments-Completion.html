Design DNA — "The Dotted Route"

The brand icon set is a family of dashed route lines and a dashed location pin. That becomes the system's one signature: every journey, progress state, and trust moment in the app is drawn as a dotted route — map polylines, the office-matching stepper, dividers between pickup and drop-off, and the loading motion on splash. Everything else stays quiet: white surfaces, warm gray canvas, purple for trust, orange spent only where the rider acts.

The signature in use

One bold element, used with discipline
  • Map route polylines (purple dots → orange destination)
  • Office-matching progress stepper
  • Pickup→drop-off dividers in cards & receipts
  • Splash & empty-state illustration language

Rules: radius 16–28px, 4pt spacing grid, one shadow level on cards, 48px minimum touch targets, outdoor contrast mode, WCAG AA contrast (orange never used for body text on white — only #E29200+ for text).

Service structure — source of truth

Per FleetOS Final Service Structure. The public app shows 3 main services; classes appear only after route entry; route type is detected, never chosen.
Ride
METER ONLY
City & local everyday trips. Classes: Standard · Comfort · Electric · SUV · Van · Luxury/Executive.
Premium
METER ONLY
Exotic & ultra-luxury local rides. Classes: Exotic Sport · Ultra-Luxury Sedan · Ultra-Luxury SUV. Never fixed-price; never long-distance.
Travel
FIXED A-TO-Z ONLY
All fixed-route trips. Classes: Standard · Comfort · Electric · SUV · Van · Luxury · Ultra-Luxury Travel. Route type (airport, intercity, tourism, cross-border) is detected here.
One service = one priceEach backend service is either meter or fixed, never both. Ride/Premium = meter; Travel = fixed A-to-Z.
Route detectionPickup/drop-off → backend classifies local vs airport / intercity / cross-border / tourism. Rider picks the class; FleetOS picks the route type. Never a route button on home.
Home pageOnly Ride · Premium · Travel. Taxi, Airport Transfer, Chauffeur, Tourism, Rent-a-Car, Corporate are not public services — they map into these three (Business is private/account-only).
Class guaranteeElectric / SUV / Van / Luxury / Exotic / Ultra-Luxury are guaranteed needs — dispatch must match or ask the rider to approve an alternative.
Fare labelsRide & Premium show "estimated meter"; Travel shows "fixed route". Never label both the same.
AvailabilityShow only classes & offices that can actually fulfil the trip (online, granted, priced, in geofence, with a matching driver/vehicle).

Where it's applied in this board: 04 Home (3 service cards), 06 Travel classes & 06b Ride classes (class lists + detected-route notes), 05b Availability check, and the office/confirm screens. The source code carries inline comments at each of these points marking the rule being enforced.

Flow B · Booking

04–06 · Dashboard, Route & Availability, Class

Per the FleetOS service structure: the home shows only the 3 main services (Ride · Premium · Travel). The rider picks one, sets a route, and the system detects the route type and checks availability. They then choose from only the classes that service can fulfil — meter-estimated for Ride/Premium, fixed-route for Travel — and see only offices that can fulfil that exact class. A 3-step bar (Route → Class → Office) keeps the rider oriented; the office sheet folds in payment and a single "Request ride" CTA, and route types like airport/intercity stay backend-detected, never buttons.

Journey logic

Core flows and their decision points
  • Book (on-demand): Dashboard home → pick a main service (Ride · Premium · Travel) → set route (pickup + drop-off) → availability check (backend detects route type + finds offices, ETAs, prices, eligible drivers) → pick from only the fulfillable classes of that service → see only offices that can fulfil that exact class → pick an office in a fast sheet (best pre-selected · payment folded in · optional details) → Request ride (no separate confirm step) → Matching → Accepted (with Cancel) → Arriving → Arrived → In-ride (live meter for Ride/Premium · fixed total for Travel) → Completed → Dual rating. 3-step bar: Route → Class → Office (request happens here). Rider chooses the class; FleetOS detects the route type (airport/intercity/tourism/cross-border) in the background.
  • Book (scheduled): Ride type (Airport/Travel) → Trip details → Compare fixed offers → Booked → Scheduled status (driver assigned ~2 h before) → live flow joins on-demand path at "Accepted".
  • Matching fallback: office silent 90 s or rejects → AlternativeOfficesList (same route, re-ranked) → one-tap re-request. Cancel is free pre-assignment.
  • Support routing rule: trip operations (pickup, driver, vehicle, route, lost item) → office; safety, policy, payment, refunds, unresolved tickets → FleetOS. Every support surface shows both layers in that order.
  • Driver chat (masked, post-acceptance only): in-app chat appears only after a driver is assigned — never during browsing/matching. Surfaces on Accepted, Arriving (+ floating icon when map is focus), Arrived, In-ride, and an optional post-trip follow-up. Pairs with Call; both are number-masked (neither party sees a phone number). Office is never a chat button — office support is the report/ticket flow. Driver bubbles use a higher-contrast surface for outdoor readability. Chat is visually secondary to status and Safety.
  • Rebooking loop: Completed/History/Favorites → "Rebook with this office" pre-selects office and skips marketplace (still shows price before confirm).
  • Guest mode: browse marketplace and prices; booking requires OTP login (lazy auth at Confirm).

v7/v8 implementation sync risks

Native map renderer parity + TextScaler-safe chat + support/action hierarchy
  • Map style parity: the HTML map is a CSS approximation. In Flutter, mirror #E3E0D4, #C3BEB2, #D1CCC0, #ECE8DD, #312873, and #F8A609 into a real Google Maps JSON style or Mapbox style layer.
  • Device QA: verify map contrast on real phones outdoors. Screenshot comparison alone is not enough because map renderers anti-alias roads and labels differently from CSS gradients.
  • Outdoor maps: when Outdoor Mode is active, reduce POI clutter, increase road contrast, thicken the route polyline, and strengthen pickup/drop-off markers.
  • Dynamic chat bubbles: when MediaQuery.textScaler increases text, scale bubble padding and border radius together. Do not keep fixed 9×12 padding with 14px radius for large text.
  • Chat layout rule: at large text sizes, allow quick replies and chat bubbles to wrap, increase max bubble width to ~84%, and keep input height at 48dp minimum.

v8 approval gates: native map, accessibility, support IA, short screens

These are implementation requirements, not design suggestions
  • Native map style is mandatory: do not ship with default Google Maps / Mapbox styling. Create a FleetOS map style using desaturated beige land, stronger roads, reduced POIs, FleetOS route colors, strong pickup/drop-off markers, and office-colored vehicle markers.
  • Outdoor mode changes the map: increase road contrast, thicken route polylines, reduce label clutter, enlarge car/current-location markers slightly, and add a white/dark outline around route and markers.
  • Large text must reflow: support 100%, 115%, 130%, and the maximum reasonable OS font size. Compact service cards, office cards, live meter, bottom nav, chat bubbles, safety sheet, payment recovery, and Arabic home must never clip critical text.
  • Live trip action row: show only Call driver · Message driver · Share trip · Safety. Do not show Call Office as a competing primary live-trip action.
  • Safety & Help structure: Zone 1 = Taxi Office / trip operations. Zone 2 = FleetOS / safety, payment, refund, policy, and escalation. Office support is available but not a normal chat button.
  • Short-screen home: on iPhone SE / older Android heights, the rider must see the search bar and Ride / Premium / Travel without scrolling; wallet, favorites, account, saved offices and promotions move below the fold or into collapsed QuickGlance.

Large text / accessibility checklist

Flutter layout behavior at 100%, 115%, 130% and max reasonable text scale
  • Use flexible heights, Wrap, Flexible, Expanded, and stacked breakpoints; avoid fixed-height cards for critical trip information.
  • Never ellipsize critical values: price, ETA, driver plate, safety labels, payment status, office name, and pickup/drop-off instructions.
  • At large text, office cards grow taller and price/ETA may move to a second line; live meter stacks total below time/KM if needed.
  • Chat bubbles wrap, grow to about 84% width, and scale padding/radius together with TextScaler.
  • All touch targets stay 44–48 dp minimum, including icon-only buttons and secondary text actions.
  • Arabic screens get extra vertical spacing and fewer micro-labels per card.

Implementation notes

For the Flutter team
  • Theme: single FleetTokens ThemeExtension; orange reserved for one primary action + selected prices; purple owns headers/nav/office identity. Never mix both on one element.
  • Type: Plus Jakarta Sans (EN) / IBM Plex Sans Arabic (AR) via google_fonts; display weights 700–800, body 400–600; operational metadata minimum 11 sp, body minimum 13 sp, tap targets 48 dp. Support OS dynamic type to 130%; when text scales, convert compact cards to stacked layouts.
  • Compact home rule: on iPhone SE / short-height devices, keep Search + Services + Banner above the fold; collapse saved offices and wallet into QuickGlance or move them below scroll. Never let secondary account content push booking actions down.
  • Maps: light custom map style (desaturated, no POI clutter); Outdoor Mode uses darker roads, stronger route lines, heavier markers, and fewer background details. Mirror the board map colors into Google Maps JSON / Mapbox style tokens (#E3E0D4, #C3BEB2, #D1CCC0) and QA on-device because native map rendering can drift from CSS gradients. Dotted polylines via custom PolylinePainter; office-colored car markers.
  • State: trip is a finite-state machine (requested → officeConfirmed → assigning → accepted → arriving → arrived → onTrip → completed | cancelled | rejected). UI binds to states, never to events.
  • Realtime: WebSocket trip channel; offline queue for rating/ticket submissions; cache office hotline + plate locally for active trip.
  • A11y: 4.5:1 contrast on all text, real Outdoor Mode theme via data-contrast="outdoor" / Flutter theme flag, semantic labels on contact buttons, dynamic type to 130%, high-contrast chat bubbles and map legibility checks under bright light. Chat bubble padding and radius must scale with TextScaler so larger text does not crowd the rounded bubble.
  • RTL: use EdgeInsetsDirectional / AlignmentDirectional everywhere; never hardcode left/right; wrap fares, ETAs, balances, plates, meter values and ratings with Directionality.ltr / unicode-bidi isolate so digit order never flips; test S6 layout per release.
  • Pickup usability: text actions such as Change note must keep a minimum 44 dp hit target with invisible padding; dashed borders are reserved for upload/drop/empty states, not rider actions. Use light haptics for quick replies and medium haptics for arrival/driver accepted.
  • Support IA: main live-trip row is strictly Call driver · Message driver · Share trip · Safety. Office call/ticket appears only inside Safety & Help → Taxi Office / Trip Operations.
  • Analytics: office_compared, office_selected, office_changed, call_office_tapped_from_safety, office_ticket_created, safety_opened, fleetos_escalation_started, dual_rating_submitted, rebook_same_office — the marketplace KPIs.
